## 4. Data model (Prisma)

Models: `User`, `Role`, `Permission`, `RolePermission`, `Counter` (atomic order-number sequence), `Station`, `Order`, `StationVisit`, `QcReview`, `ReworkRoute`, `DeliveryOutcome`, `OrderEvent`, `ProductCategory`, `Product`, `ProductImage`, `ProductColorLining`, `ProductPriceHistory`.

Key design calls:
- **Stations are a table**, not an enum — Management can add, rename, reorder, retire, or logo-brand a station at runtime with no code change or migration. See §4b. QC and Courier/Pick-up are rows in that same table but flagged `isSystem: true` — fixed, not Management-editable. See §4d.
- **Timeline is a separate append-only table** (`OrderEvent`), written in the same transaction as every state change — not derived at read-time from other tables, so it can't drift.
- **Rework and returns reuse the same mechanic**: both reopen a new `StationVisit` (incrementing `sequenceNo`) rather than mutating the original visit.
- Full schema: `prisma/schema.prisma`.

### 4a. Product catalog

Added after Phase 1's initial build, replacing intake's original free-text `carModel`/`productType` fields with real catalog references — `Order.productId` (required) and `Order.colorLiningId` (optional).

- **`ProductCategory`** — the car brand (Ford, Honda, Hyundai, Isuzu, Kia, Mazda, Mitsubishi, Nissan, Suzuki, Toyota, seeded by default). Management-only to create/edit; everyone can read (needed to populate the intake picker).
- **`Product`** — belongs to one category. Carries `name`, `description`, `regularPrice`, `salePrice`, `rating` (all plain `Float`, not `Decimal` — a deliberate simplification since this app doesn't do payment/ledger math, just catalog display), plus `isActive`.
- **`ProductImage`** — many per product, ordered, one flaggable as primary. The only hard-deletable child (no order ever references an image directly, so removing a bad one is safe).
- **`ProductColorLining`** — many per product (e.g. "Black Lining", "Red Lining"), **scoped per-product** rather than one global list, matching how the live reference listings actually vary by product. Soft-toggled (`isActive`), never hard-deleted, because an `Order` can reference one historically.
- **Intake validation** (`orders.service.ts`): a product must be active to be ordered; if it has any active color linings, `colorLiningId` becomes **required**; if it has none, one must **not** be supplied.
- **Images are URLs, not uploads.** There's no file-upload/storage endpoint — Management supplies a URL to an already-hosted image. See gap below.
- **Price is snapshotted onto the order, not live-joined from the product.** `Order.unitPrice` (what was actually charged — `salePrice` if one was active, else `regularPrice`) and `Order.regularPriceAtOrder` (the undiscounted price at that moment, so the discount given can be derived later) are captured once, either at intake or whenever `productId` is changed on an existing order via `PATCH /orders/:id`. Editing anything else on the order (including just the color lining) never touches these. This was a deliberate fix — the initial catalog build had no price snapshot at all, meaning a later price change or removed sale would have silently changed what every past order "cost" when viewed through the live product.
- **`ProductPriceHistory` tracks every price change on the product side, separately from the order snapshot above.** Append-only — a new row is written (via `POST /products`, and `PATCH /products/:id` whenever `regularPrice` and/or `salePrice` actually differ from the current value) capturing the new `regularPrice`/`salePrice` plus who changed it and when. Unrelated edits (name, description, images, `isActive`, ...) never add a row. Read via `GET /products/:id/price-history` — Supervisor+, same tier as the order turnaround report, since this is pricing/historical data rather than everyday catalog browsing.
- **Per-order discounts** (`Order.discountAmount` / `discountReason`) are a distinct layer on top of `unitPrice` — for a negotiated/loyalty/goodwill discount on one specific order, as opposed to a product-level sale (which is already baked into `unitPrice` via `salePrice`). `finalPrice` (`unitPrice - discountAmount`, computed on read, not stored) is what the customer actually pays. **Deliberately only settable via `PATCH /orders/:id`, never at intake** — intake is Staff+, but discounting is treated as a Supervisor+ action like every other price-sensitive one in this app, so it's gated by that route's existing role check rather than adding new field-level permission logic. Workflow: Staff takes the order normally; if a discount is warranted, a Supervisor applies it as a follow-up edit. Validated server-side (`0 ≤ discountAmount ≤ unitPrice`); if a product swap (via the same or a later edit) drops `unitPrice` below an existing discount, the discount is silently reset to 0 rather than allowed to produce a negative `finalPrice`.

### 4b. Dynamic stations

Stations used to be a fixed 6-value enum baked into the code (`CUTTING`, `SEWING`, `EMBROIDERY`, `QC`, `PACKAGING`, `COURIER_PICKUP`). They're now a `Station` table, Management-editable via `/stations`, and the whole workflow engine (`src/lib/workflow.ts`) was rewritten to be data-driven instead of hardcoding a sequence.

- **`Station` fields**: `name`, `logoUrl` (a URL, same "no upload endpoint" caveat as product images), `slug` (auto-derived, stable id), `sortOrder` (defines the production sequence — no more hardcoded array), `isActive` (retire without breaking history), `description`, `colorHex` (for dashboard chips, since station names are no longer a known fixed set the frontend can hardcode colors for), and `isQcCheckpoint`.
- **`isQcCheckpoint`** replaces the old assumption that "QC" was a single special enum value. Any station can be flagged as a checkpoint: it exits via `POST /orders/:id/qc-decision` (approve/rework) instead of a plain outgoing scan, and can route rework backward. There's no limit on how many checkpoint stations exist.
- **Rework targeting rule (explicit decision, not assumed):** a checkpoint can route rework to **any active station with an earlier `sortOrder`** than itself — not a fixed pair like the old `[Cutting, Sewing]`. Confirmed with the user rather than guessed, since the alternative (an explicitly-configured allow-list per checkpoint) was a real option with schema implications.
- **Reordering is blocked while any order is in progress.** Because `nextStationAfter`/`lastStation` are always computed *live* from current `sortOrder` values (never fixed per order at intake — unlike price, which *is* snapshotted), changing a station's `sortOrder` mid-flight could silently skip a station an in-progress order hasn't been to yet, or shift what counts as "last." `PATCH /stations/:id` now rejects an actual `sortOrder` change with `409` if `Order.count({ status: IN_PROGRESS }) > 0` (`stations.service.ts`) — confirmed with the user rather than assumed, since the alternatives (snapshot each order's route at intake, or leave it as a documented operational rule) were both real options too. Other station edits (name, logo, color, `isQcCheckpoint`, `isActive`) are unaffected and still work anytime.
- **`Order` no longer has `currentStage`/`currentStation` (enum-based).** Replaced with `status` (`IN_PROGRESS` | `DELIVERED` — the only real terminal state), `currentStationId` (FK, nullable only once delivered), and `isCheckedIn` (bool — physically at `currentStationId` vs. in transit toward it). "Returned" is not a persisted status; it's an event (`DeliveryOutcome.outcome = RETURNED`) that re-points `currentStationId` at the responsible station and continues the same state machine.
- **"Last station"** (used to gate delivery-outcome recording) is now computed as whichever active station has the highest `sortOrder`, not a hardcoded `COURIER_PICKUP` reference.
- Scan/QC/delivery request bodies now take `stationId` (not an enum value) — see `/docs` for exact shapes.
- Local Postgres now has a `SHADOW_DATABASE_URL` configured (see `.env.example`) — needed to unblock `prisma migrate dev`'s drift detection, and worth keeping for all future migrations, not just this one.

### 4c. Dynamic roles & permissions

Roles used to be a fixed 3-value enum (`PRODUCTION_STAFF`, `SUPERVISOR`, `MANAGEMENT`) with every route gated by a hardcoded role-list. Following the exact same "enum → Management-editable table" pattern as §4b, roles are now fully dynamic — same motivation, same precedent, extended into authorization itself this time rather than the production workflow.

- **`Permission` is a fixed, code-defined catalog (13 entries) — deliberately *not* Management-creatable.** Each slug (e.g. `orders.edit`) corresponds to a hardcoded `fastify.authorize(slug)` call at one specific route; a permission invented via the API wouldn't be wired to anything. Read-only via `GET /permissions`. This is the one real difference from Stations, which are pure configuration data with no code-level meaning tied to any single row.
- **`Role` + `RolePermission`** are freely Management-editable via a new `roles` module (`GET/POST /roles`, `PATCH /roles/:id`) — same shape as Stations/Categories (soft-toggle `isActive`, no delete, auto-derived `slug`). `PATCH` can replace a role's entire permission set in one call.
- **Default seeded roles reproduce the original 3-tier behavior exactly** (see `prisma/seed.ts`): Management gets all 13 permissions; Supervisor gets 8 (create/edit/QR-regen/report/price-history/scan/QC/delivery); Production Staff gets 4 (create/scan/QC/delivery).
- **Authorization is resolved live from the database on every `authorize()` call — the JWT is never trusted for the actual decision.** One indexed query (`src/plugins/rbac.ts`) re-resolves the user's *current* role and whether it holds the requested permission, using only the user id from the token. This means revoking a permission from a role, *or* reassigning a user to a different role entirely, takes effect on the very next request — no re-login required. Verified directly: stripped `orders.edit` from the Supervisor role mid-session and the already-issued token immediately started 403ing; separately, reassigned a user's role mid-session and the same token immediately picked up the new permission set. As a side effect this also closes a pre-existing gap — a deactivated user's token used to keep working until its 12h expiry on any `authorize()`-gated route; now it stops immediately. Deliberately *not* extended into plain `fastify.authenticate` (pure JWT-signature check stays free) — only the create/edit/manage routes that already carried `authorize()` get the live guarantee; read-only list/detail routes keep today's performance profile. Deliberately no time-based permission cache either — it would just reintroduce the staleness window this design removes.
- **Lockout-prevention guard, and it's stricter than the obvious version.** The naive guard ("don't allow zero active *roles* holding `users.manage`/`roles.manage`") has a real hole: a role can stay active while every user on it gets deactivated or reassigned elsewhere. The actual invariant enforced (`src/lib/adminGuard.ts`, `assertAdminAccessRetained`): **at least one currently-active user, on a currently-active role, must hold `users.manage` and `roles.manage` at all times.** Runs inside the same transaction as both `PATCH /roles/:id` (when `isActive`/`permissionSlugs` is touched) and `PATCH /users/:id` (when `isActive`/`roleId` is touched) — a violation rolls the whole edit back. No superuser bypass exists (same no-bypass precedent as Stations) — this guard is the *only* protection, so both surfaces had to be covered, not just the role-editing one. Verified: attempting to strip `roles.manage` from the sole admin-capable role, and separately attempting to deactivate the sole Management user, both correctly 409 and roll back; both succeed once a second admin-capable user exists.
- **Accepted residual risk, not engineered around:** under Postgres read-committed isolation, two concurrent admin edits could theoretically both read "count = 1" and both commit, reaching zero coverage. Given this is a small internal admin tool where concurrent role/user edits by different Management users are extremely unlikely, this was a deliberate choice not to upgrade to `SERIALIZABLE` or add row locks for it.
- **No manual recovery runbook has actually been written yet** for the catastrophic case (a guard bug, or every Management credential lost) — since there's no bypass, recovery would mean direct SQL/Prisma Studio against `role_permissions`/`users`. Flagged as a real gap below, not just a footnote.
- **Ripple effects**: the JWT payload and `/auth/login`/`/auth/me` responses now carry `roleId` + `roleName` (display-only) instead of a `role` enum string. The order timeline's actor objects and product price-history's `changedBy` objects carry a flat `roleName: string | null` (live, not a snapshot of what the role was at the time) rather than a role object — nothing downstream needs to filter by role id/slug there, so it wasn't worth coupling those schemas to the full shape.
- **Destructive local migration.** This was an enum→FK conversion with no local data worth preserving and nothing deployed yet, so it went through `prisma migrate reset` (drop+recreate+reseed) with the user's explicit consent (Prisma's own safety check for AI-invoked destructive commands required it) rather than an in-place data migration.

### 4d. Station-worker assignment + fixed QC/Delivery stages

Triggered by a real client requirement surfaced mid-session: "the clients wants to assign users to specific stations... if the user was a station worker then he can be selected under stations assigning of worker." Working through it with the user also surfaced a bigger, unprompted scope change: QC and Courier/Pick-up should no longer be treated as Management-configurable dynamic stations at all — they're fixed stages every order passes through, in a fixed position, still with their own physical receive/outgoing scans for timeline accuracy.

- **QC and Courier/Pick-up stay rows in the `Station` table** (not pulled out into separate models) — they still need the exact same receive/outgoing `StationVisit` mechanics (and QC still needs `isQcCheckpoint`'s decision-based exit) as every dynamic station, so reusing that machinery was far less risky than parallel-building a second pipeline concept. What changes is a new `Station.isSystem: Boolean` flag: `PATCH /stations/:id` now flatly rejects **any** edit to a system station (`stations.service.ts`), and `POST/PATCH /stations` reject `isQcCheckpoint: true` from a **dynamic** station too — otherwise Management could recreate a second, arbitrary QC gate, defeating the whole point. Only the two seeded system stations (QC, Courier/Pick-up) can ever carry `isQcCheckpoint`/`isSystem: true`, and only via `prisma/seed.ts`.
- **System stations always sort after every dynamic station, regardless of raw `sortOrder` numbers.** `workflow.ts`'s `activeSorted()` partitions active stations into non-system (sorted by `sortOrder`) then system (sorted by `sortOrder` among themselves) and concatenates — no reserved numeric range to maintain. `nextStationAfter()` was rewritten to walk that array by index instead of comparing raw `sortOrder` values, since a system station's own `sortOrder` (0, 1, …) has no fixed relationship to whatever values Management assigns dynamic stations. `GET /stations` mirrors the same ordering (`orderBy: [isSystem, sortOrder, name]`) so the list view matches the real production sequence.
- **Rework targeting simplified as a side effect**: `isValidReworkTarget` no longer compares `sortOrder` at all — since QC always runs after every dynamic station now, "any active dynamic station" and "any earlier active station" became the same rule. System stations (QC, Courier) are explicitly excluded as rework targets.
- **Real gap found and fixed while implementing this**: the pre-existing `canRecordDeliveryOutcome` check (`isCheckedIn: false` + `currentStationId === lastStation.id`) can't tell "in transit toward the last station" apart from "actually scanned out there" — both produce the exact same state tuple, since there's no station after the last one to disambiguate via a receive step. This meant a delivery outcome could previously have been recorded the instant QC approved, without Courier/Pick-up ever being physically scanned — silently defeating the user's explicit "delivery needs to punch in and out... for timeline purposes" requirement. Fixed in `delivery.service.ts`: now requires a `StationVisit` at the last station with `outgoingAt` set **and** newer than the most recent `DeliveryOutcome` row (guards the RETURNED-then-immediately-redelivered edge case, where a stale closed visit from before the return could otherwise satisfy the check without any new scan). This bug predates this feature — it existed whenever Courier/Pick-up was simply the highest-`sortOrder` dynamic station — but only became consequential once "must physically punch in/out" was made an explicit requirement.
- **Station assignment**: new `User.assignedStationId` (nullable FK to `Station`), enforced as **one station at a time**, per the user's confirmed choice. Settable on any user via `POST/PATCH /users` regardless of role (deliberately not hardcoded to only the `station-worker` role slug — consistent with this app's "roles are just data" philosophy; a Supervisor could theoretically be assigned too, though the UI would presumably only surface the picker for the Station Worker role). Must reference an **active, non-system** station — assigning a worker to QC/Courier is rejected, since those are handled by whoever holds `qc.decide`/`delivery.record`/`scan.perform` generally, not by a per-worker assignment.
- **Enforcement is a real restriction, not just a label**: `POST /scan/receive` and `POST /scan/outgoing` both look up the acting user's `assignedStationId` before touching the order; a mismatch 403s ("You are only assigned to scan at X"). Deliberately scoped to just the scan endpoints — `qc.decide`/`delivery.record` aren't station-restricted, since a Station Worker doesn't hold those permissions by default anyway (see below), and extending the restriction there wasn't asked for.
- **New default seeded role: Station Worker** (`station-worker` slug) — `scan.perform` only, per the user's explicit choice. A demo account (`stationworker@rascorp.test`) is seeded assigned to the first dynamic station (Cutting).
- **Verified end-to-end** (manual, same pattern as §4b/§4c): full order walked through all 4 dynamic stations → QC receive+approve → Courier/Pick-up receive+outgoing → delivery outcome recorded, confirming QC/Courier both log real `StationVisit` receive/outgoing timestamps the whole way; delivery-outcome 409s before Courier's outgoing scan and succeeds right after; QC rework accepted for a dynamic station, rejected for a system station; a dynamic station creation/edit attempting `isQcCheckpoint: true` 400s; a system station 409s on any `PATCH`; the station-worker account 403s scanning at a station other than Cutting and succeeds at Cutting; assigning a user to QC 400s.
- **Not addressed**: no restriction was added preventing a *non*-station-worker role (e.g. Supervisor) from also being given an `assignedStationId` — the field is generically available on `User`, and only the frontend's UI choice of when to show the station picker enforces the "only station workers get assigned" convention from the original request. Worth confirming this is fine, or whether a stricter role-based gate is wanted later.

### 4e. Refresh tokens

Raised by the user while reviewing the auth design: the original JWT setup had a single 12h access token with no way to extend a session without a full re-login, and no way to revoke a specific token early (lost device, forced logout). Neither had been a deliberate trade-off — refresh tokens just weren't part of the original scope.

- **Access tokens dropped from 12h to 15 minutes.** The whole point of adding refresh is to shrink a leaked access token's blast radius — keeping the old long expiry alongside a refresh token would have gotten none of that benefit. Sessions stay seamless via silent refresh (frontend's job, not yet built), not a long-lived access JWT.
- **Refresh tokens are opaque random values (`crypto.randomBytes(40)`), not JWTs** — there's no reason to make them self-describing since every one is looked up and validated against the database anyway. Only a sha256 hash is ever stored (`RefreshToken.tokenHash`, unique) — sha256, not bcrypt, because a refresh token is already high-entropy random data, not a low-entropy human password; the raw value is returned to the client once, at issuance/rotation, and never persisted.
- **Rotate-on-use with reuse detection.** `POST /auth/refresh` always revokes the token it was given and issues a new one in the same `familyId` (a random id assigned once at login, threaded through every rotation descended from it). If an *already-revoked* token is presented again, that's treated as a signal of theft (a legitimate client only ever holds the newest token) — the entire family is revoked in one `updateMany`, killing every token from that login, not just the one reused. Verified: rotated once, replayed the old token → 401 + family killed; the *new* token issued by the legitimate rotation was then also dead, confirming the blast radius covers the whole chain, not just the stolen token.
- **`POST /auth/logout`** revokes one specific refresh token (ends that one device's session) — requires a valid access token, and the refresh token must belong to that same user. Doesn't touch the still-live access token itself (nothing to revoke there; it just expires naturally within 15 minutes). Idempotent — logging out twice isn't an error.
- **Deactivation is honored on refresh, not just on the initial gate.** `rotateRefreshToken` re-checks `user.isActive`/`role.isActive` on every exchange — a user deactivated mid-session can't keep refreshing their way to new access tokens for the remaining days of the refresh token's life.
- **`GET /auth/login` and `POST /auth/refresh` both now return `user.permissions`** (see the live-permissions work earlier this session) — refresh doubles as a cheap way for the frontend to silently re-sync a user's display info and permission set alongside getting a new access token.
- **Known gap, not yet addressed**: no periodic cleanup of expired/revoked rows in `refresh_tokens` — the table only grows. Fine at this app's expected scale, but a scheduled prune job (e.g. delete rows where `revokedAt` or `expiresAt` is well in the past) would be the natural follow-up before this sees heavier use.
- **Not built**: a "log out everywhere" endpoint that revokes every family for a user at once (as opposed to one device via `POST /auth/logout`, or deactivating the account entirely which achieves the same thing via the check above). Wasn't asked for; easy to add later if needed (revoke all `RefreshToken` rows for a `userId` where `revokedAt` is null).

### 4f. Order archiving

Added 2026-08-20, closing the "no order delete/archive endpoint" gap flagged in §6. `POST /orders/:id/archive` / `POST /orders/:id/unarchive`, gated by a new `orders.archive` permission (Management + Supervisor by default, same tier as `orders.edit`).

- **Fully frozen, not just hidden** — an archived order (`Order.isArchived` + `archivedAt`) is rejected with 409 (`assertNotArchived` in `orders.service.ts`) from every mutating order action: `PATCH /orders/:id`, scan receive/outgoing, QC decision, delivery outcome, and QR regeneration. Verified live: scanning an archived order 409s ("Order RC-... is archived — unarchive it first").
- **Any status can be archived** — deliberately not restricted to `DELIVERED`, since the main real-world case (a bad/test intake) is usually still `IN_PROGRESS`.
- **Hidden from the dashboard by default, not deleted** — `GET /orders` excludes `isArchived: true` unless `includeArchived=true` is passed, same pattern as `includeInactive` on products/categories. `GET /orders/:id` still returns an archived order directly, same as retired products/categories.
- **Idempotent** — archiving an already-archived order (or unarchiving an already-active one) is a no-op, same pattern as `POST /auth/logout`; no duplicate `OrderEvent` row is written.
- **Recorded on the order's own timeline**, not `ActivityLog` — new `OrderEventType.ARCHIVED`/`UNARCHIVED` values, written in the same transaction pattern as every other order-lifecycle action, and broadcast over the SSE stream via `publishOrderEvent`.
- Verified end-to-end locally: archive → excluded from default list, included with `includeArchived=true`, scan blocked (409) → unarchive → scan works again; a role without `orders.archive` (Production Staff) 403s on the archive endpoint.

### 4j. Archived-only order filter, and concerns across every order

Added 2026-08-20, closing two gaps surfaced while listing out what a frontend dashboard would actually need.

- **`GET /orders?archivedOnly=true`** — new filter on the existing `listOrders`/`ListOrdersFilter`. Previously `includeArchived=true` only ever *mixed* archived and active orders together (matching the same `includeInactive` convention used by products/categories/stations) — there was no way to see only archived orders, which an "Archived Orders" admin screen needs. `archivedOnly` overrides `includeArchived` when both are set.
- **`GET /orders/concerns?isResolved=&page=&pageSize=`** — concerns/clarifications across every order, not just one (`GET /orders/:id/concerns` already existed, scoped to a single order). Paginated, newest first, each item carries an `order: {id, orderNumber, customerName}` summary so a cross-order "open concerns" panel doesn't need a second lookup per row. Batch-resolves actors once for the whole page (unlike the per-order `listConcerns`/`toConcernDto`, which does one actor query per item — fine for one order's handful of concerns, not for a potentially-large global list). Gated by `orders.report.view` (Supervisor+), same tier as the QC/sales reports — a single order's own concerns stay visible to any authenticated user via the existing endpoint.
- **Bug caught and fixed during smoke-testing**: the new `isResolved` query param was first written as `z.coerce.boolean()`, which is broken for this exact case — `Boolean("false")` is `true` in JavaScript, so `?isResolved=false` would silently return *resolved* concerns instead of open ones. Fixed by parsing the literal `"true"`/`"false"` string values instead of coercing. Worth knowing: every other boolean query filter in this codebase (`overdue`, `includeArchived`, `isCheckedIn`, etc.) uses the same `z.coerce.boolean()` pattern and has the same latent bug — it just hasn't bitten yet because those are all "presence implies true" flags callers only ever omit or set to `true`, never explicitly pass `=false`. Not fixed elsewhere since nothing currently depends on `=false` working for those; flagging here so it's not forgotten if a caller ever needs `?overdue=false` or similar to work correctly.
- Verified: `archivedOnly=true` returns exactly the one currently-archived test order and nothing else; the default listing still excludes it; the global concerns endpoint correctly returns the seeded resolved concern under `isResolved=true` and an empty list under `isResolved=false`; a role without `orders.report.view` (staff) 403s on it.
- **Not yet deployed** — local only, per the standing don't-redeploy-without-asking rule.

### 4k. Station-level rework rejection (`POST /scan/reject`)

Added 2026-08-20, a real client request: previously the *only* way to send an order back for rework was the formal QC decision at the fixed QC checkpoint (the very last stage) — a regular station midway through the sequence that spots a defect from an earlier station had no way to act on it directly; the order had to travel all the way to QC first.

- **Scope, confirmed with the user rather than assumed**: any regular (non-system) station can now reject the order it just received, but only back exactly **one step** — to whichever active station immediately precedes it in the production sequence (`workflow.ts`'s new `previousStationBefore`), not to an arbitrary earlier station like QC's rework can. The first station in the sequence has nothing before it, so rejection there 409s. QC and Courier/Pick-up (system stages) keep using their own dedicated flows (`qc-decision`, `delivery-outcome`) — this new path 409s if attempted there.
- **`POST /scan/reject`** (`{qrToken, stationId, rejectionReasonId?, reason?}`) — same `scan.perform` permission and `assertStationAllowed` station-worker lock as `/scan/receive`/`/scan/outgoing`. Closes the current station's open `StationVisit`, creates a `ReworkRoute` (with `qcReviewId: null` — the model's `qcReviewId` was made nullable, since no formal `QcReview` is involved), and moves the order back. Writes `OrderEventType.STATION_REJECTED` then `REWORK_ROUTED` (new event type; mirrors QC's `QC_DECISION`+`REWORK_ROUTED` pair), so it shows up in `/orders/:id/timeline` exactly like a QC rework does.
- **Reuses the QC rejection-reason catalog** (`rejectionReasonId`, optional) — same catalog and field as `qc-decision`'s REWORK path, by explicit choice, so both feed the same `GET /orders/reports/qc` breakdowns.
- **Reporting nuance worth knowing**: `GET /orders/reports/qc`'s `totalReviews`/`approvedCount`/`reworkCount`/`reworkRatePercent` only ever counted formal `QcReview` rows and still do — a `/scan/reject` rejection never creates one, so it's out of scope for those four fields. `byStation`/`byRejectionReason` are queried directly off `ReworkRoute` with no `QcReview` join, so they *do* pick up both QC and station-level rejections — meaning `byStation`/`byRejectionReason` can sum to more than `reworkCount`. Documented explicitly in each field's schema description so a dashboard built on this doesn't read it as a bug.
- Verified end-to-end locally: rejecting before being checked in 409s; rejecting at the first station 409s ("no earlier station"); rejecting at a QC/system station 409s with the dedicated-flow message; a station worker rejecting at a station other than their assignment 403s; a real Cutting→Test Station Audit rejection with a rejection reason correctly moves the order back, appears in the timeline as `STATION_REJECTED`→`REWORK_ROUTED`, and shows up in the QC report's `byStation`/`byRejectionReason` breakdowns; rejecting an archived order 409s.
- **Not yet deployed** — local only, per the standing don't-redeploy-without-asking rule.

### 4l. `assignedStationId` on login/refresh/me

Added 2026-08-20, a real frontend bug report: a Station Worker's own assigned station was never returned anywhere in the auth flow — `POST /auth/login`, `POST /auth/refresh`, and `GET /auth/me` all omitted `assignedStationId` entirely. Since `GET /users` (the only endpoint that has it) is Management-only, a Station Worker's own frontend had **no way at all** to learn its own assigned station — not even indirectly.

Null for roles with no station restriction (Supervisor, Management).

- `auth.service.ts`'s `ROLE_WITH_PERMISSIONS_INCLUDE` (shared by `verifyLogin`/`rotateRefreshToken`) now also includes `assignedStation: {id, name}`.

### 4m. Station queue endpoint (`GET /stations/:id/queue`)

Added 2026-08-21, in response to a frontend mockup of a station-worker "Cutting queue" screen (badges: Pending / In progress / Rework / QC flag, each order showing "Returned by Embroidery · seam misaligned" style context). Two real gaps surfaced: nothing said *why* an order was sitting at a station (fresh vs. forward hand-off vs. rejected-back vs. QC-rerouted), and there was no clean "queued since" timestamp distinct from `updatedAt` (which changes for unrelated edits too).

- **`ReworkRoute.fromStationId`** (new, nullable FK to `Station`) — the station that actually rejected the order: the QC checkpoint for a formal QC decision, or the regular station for a `POST /scan/reject`. Set at both creation sites (`qc.service.ts`'s `submitQcDecision`, `scan.service.ts`'s `returnForRework`). Nullable only because rows created before this migration don't have it (verified: pre-migration rows correctly show `fromStation: null` rather than guessing); every row created going forward has it. Required adding an explicit `@relation("ReworkRouteTarget"/"ReworkRouteFrom")` name to both of `ReworkRoute`'s station relations, since a model can't have two unnamed relations to the same target model.
- **`INTAKE_CREATED` events now carry `stationId`** (the first station) — previously only the SSE broadcast had it, the persisted `OrderEvent` row didn't, which was one of the two gaps below.
- **`GET /stations/:id/queue`** — every order currently at a station (pending *or* checked in), each annotated with:
  - `arrival.type`: `NEW` (fresh intake) / `FORWARD` (normal hand-off) / `REWORK` (a regular station's own rejection) / `QC_REROUTE` (QC's rework decision) / `RETURNED` (a customer return re-entered here) — derived from the single most recent of `{INTAKE_CREATED, STATION_OUTGOING, REWORK_ROUTED, RETURNED_TO_SENDER}` events for that order (whichever is chronologically last must be what put it at its current station, since state transitions are sequential — no need to filter by destination station).
  - `arrival.fromStation`/`reason`/`rejectionReason` — resolved from the matching `ReworkRoute` for `REWORK`/`QC_REROUTE`, or the prior station for `FORWARD`.
  - `arrival.since` — the open `StationVisit.receivedAt` if checked in, otherwise the arrival event's timestamp — not `Order.updatedAt`, which is too broad (changes on unrelated edits).
  - Bucketed `counts`: `pending` (not checked in, not rework/QC-flagged), `inProgress` (checked in, regardless of arrival type), `rework`, `qcFlag`.
  - Implementation note: batches 2-3 queries and reduces "latest per order" in JS rather than raw SQL — station queues are bounded (a handful to a few dozen orders), unlike the sales report's whole-history aggregation which genuinely needs `date_trunc`.
- Verified end-to-end with a full realistic scenario: a fresh order at its first station → `NEW`; a normal forward hand-off → `FORWARD` with the correct `fromStation`; a checked-in order → `inProgress` regardless of how it arrived; a fresh `/scan/reject` → `REWORK` with `fromStation`/`reason` populated via the new `fromStationId` field; two pre-migration QC reroutes correctly show `fromStation: null` (expected, not a bug) while still counting correctly as `QC_REROUTE`/`qcFlag`. Bucket counts matched hand-computed expectations exactly across a 5-order mixed queue.
- **Still not modeled**: product size variants (only color/lining exist today) and any "on shift" presence — both flagged separately, neither built.
- **Not yet deployed** — local only, per the standing don't-redeploy-without-asking rule.

### 4n. Admin station override (`POST /orders/:id/override-station`)

Added 2026-08-21, a real request: give Management a way to directly correct a stuck or mis-scanned order — and pin it to one specific worker — without walking it back through the real scan/QC/delivery workflow.

- **Gated by a new `orders.override_station` permission — Management-only by design**, not granted to Supervisor/Production Staff/Station Worker in the default seed. `PERMISSION_DEFS` in `prisma/seed.ts` now has 17 entries (was 16).
- **Can target any active station, including QC/Courier (system stages)** — confirmed with the user rather than assumed, since this is a deliberate bypass of the formal QC-approval and physical-delivery-scan gates described in §4d. Fully audited (see below), so misuse is at least traceable, but nothing stops it structurally beyond the permission gate.
- **Marks the order as physically checked in immediately** — closes any open `StationVisit` at the old station (`outgoingAt`/`outgoingByUserId` set) and opens a new one at the target (`receivedAt`/`receivedByUserId`, `sequenceNo` incremented), exactly like a real receive scan would, so per-station duration reporting isn't corrupted by a phantom gap.
- **New `Order.assignedWorkerUserId`** (nullable FK to `User`) — pins the order to one specific worker, distinct from `currentStation.assignedWorkers` (everyone generally assigned to wherever the order is). Must reference a user whose `assignedStationId` matches the *target* station, or the call 400s. **Never carries over between overrides** — a call that changes station without re-supplying `assignedWorkerUserId` resets it to `null`, since a pin to the old station's worker wouldn't make sense once the order has moved. Exposed on every order response as `assignedWorkerUserId`/`assignedWorker: {id, name} | null`.
- **One consolidated `OrderEvent` per call** (`STATION_OVERRIDDEN`, new enum value) rather than synthesizing fake `STATION_OUTGOING`/`STATION_RECEIVED` pairs for something that didn't happen through a real scan — carries `fromStationId`/`toStationId`/`previousAssignedWorkerUserId`/`assignedWorkerUserId`/`reason` in `metadata` for a full audit trail, and shows up on `/timeline` and the SSE stream like every other transition.
- **`GET /stations/:id/queue` recognizes it** — added `STATION_OVERRIDDEN` to the arrival-event lookup and a new `"OVERRIDE"` `arrival.type` (alongside `NEW`/`FORWARD`/`REWORK`/`QC_REROUTE`/`RETURNED`), so an overridden order doesn't show a stale prior arrival reason. `fromStation`/`reason` are left `null` for this type — a deliberate simplification (the detail lives in the event's `metadata`, not surfaced there yet) rather than an extra query per queue item.
- Same freeze rule as everything else: 409s on an archived order (`assertNotArchived`, reused).
- Verified end-to-end locally: a worker not assigned to the target station 400s; a valid override moves the order and checks it in; overriding again with a matching worker sets the pin; overriding to a system station (QC) succeeds; a role without the permission (Production Staff) 403s; the archived-order 409 holds; the station queue shows `arrival.type: "OVERRIDE"`; both events appear correctly on `/timeline` with full metadata.
- **Not yet deployed** — local only, per the standing don't-redeploy-without-asking rule.

### 4o. Customer table (`/customers`), replacing free-text `customerName`/`customerContact`

Added 2026-08-21. Orders previously carried `customerName`/`customerContact` as free-text fields with no real identity behind them — the same person typed twice read as two different customers, and there was no way to answer "how many times has this customer ordered." This introduces a real `Customer` model, explicitly as prep for an eventual client-facing portal (still out of scope for Phase 1 — see §6 — where a customer will eventually sign in by email and complete their profile), while immediately enabling order-count/history lookups today.

- **All 8 orders that existed at the time were deliberately wiped first** (by user request, same session) specifically to sidestep a fuzzy backfill/dedup problem — two "carlo"s with no distinguishing contact info could otherwise have been wrongly merged into one `Customer`. This meant the `customerId` migration could be a clean, non-nullable column from day one with no data-migration script.
- **Strictly two-step intake, no free text anywhere** — a customer must already exist (`POST /customers`) before they can be found (`GET /customers?search=`) or referenced at intake. `POST /orders` takes a required `customerId` and nothing else customer-shaped; there is no inline `{name, phone, email}` path and no server-side matching/dedup logic. This was an explicit reversal mid-design — an earlier one-step "match-or-create inline at intake" approach was scoped and then deliberately dropped by the user in favor of this stricter model.
- **`Customer` fields**: `name` (required), `phone` (optional), `email` (optional, **unique** — nulls don't collide). Split into separate fields rather than one free-text contact string specifically because the future portal will log in by email and want a clean uniqueness constraint; cheap to enforce now, painful to retrofit once real duplicate emails exist.
- **Full CRUD + archive, mirroring the `Order` archive pattern exactly** (`isArchived`/`archivedAt`, freeze + hide-by-default, idempotent, reversible) rather than the simpler soft-toggle-only pattern Stations/Categories use — a customer record can turn out to be a duplicate/bad entry the same way a bad order intake can. An archived customer 409s on edit and can't be selected for a new or edited order until unarchived.
- **No new permission slugs** — reuses `orders.create` (create), `orders.edit` (edit, and repointing `customerId` on an existing order via `PATCH /orders/:id`), and `orders.archive` (archive/unarchive), consistent with treating customer management as a sub-capability of order intake rather than its own admin domain. `GET /customers`/`GET /customers/:id` are open to any authenticated user, since intake needs to search customers regardless of role.
- **Order-count/history**: `GET /customers/:id` returns `orderCount` (live `_count` on the `orders` relation, includes archived orders — a true lifetime total). Full order history is available two ways — the generic `GET /orders?customerId=X` filter (new, same pattern as `stationId`/`categoryId`), and a dedicated `GET /customers/:id/orders` (added same day, same shape/filters as `GET /orders` minus `customerId` itself, plus a 404 if the customer doesn't exist — same "thin wrapper over `listOrders`" pattern as `GET /users/:id/completed-orders`, §4g).
- **No `ActivityLog` entries for Customer create/edit/archive** — deliberately consistent with the existing split in this codebase: `ActivityLog` is documented as covering only the 5 Management-only admin-config resources (`User`/`Role`/`Station`/`Category`/`QcRejectionReason`); `Customer` creation is routine Staff+ business activity like `Order` creation, which also isn't logged there (it has its own `OrderEvent` trail instead). `Customer` has no per-record event log of its own — not needed yet at this scale.
- **Ripple effects**: `orders.schemas.ts`'s `orderDtoSchema` now carries `customerId` + `customer: {id, name, phone, email}` instead of the two free-text fields; `listOrders`'s `search` filter now matches `customer.name` via the relation instead of a flat column; the cross-order concerns endpoint (`GET /orders/concerns`, §4j) still returns `order.customerName` in its response shape unchanged — internally it now resolves that through `order.customer.name`.
- **Not yet deployed** — local only, per the standing don't-redeploy-without-asking rule.

- **"Sales Agent" role assumption.** The spec names a Sales Agent as who performs intake, but the confirmed login roles are only Production Staff / Supervisor / Management. Intake was implemented as allowed for **any** of the three (Staff+) — worth confirming that's actually right for how RasCorp's floor works.
- **Overdue detection is read-time only, not pushed.** Nothing pages/notifies anyone when an order goes overdue — it only shows up as a flag when someone queries the dashboard. No alerting channel (email/SMS/Slack) exists.
- **No rate limiting / brute-force protection on `/auth/login`.** Currently unlimited login attempts.
- **No station reorder-collision handling.** `sortOrder` isn't a unique constraint — two stations can technically share a value, in which case ordering falls back to name. Not a bug, but Management could confuse themselves by leaving `sortOrder` gaps out of sync with intent. A future admin UI should probably enforce/renumber it visually rather than exposing the raw integer.
- **`isQcCheckpoint` toggling is now moot for dynamic stations** (§4d resolved this) — only the fixed, seed-only QC system station can ever carry it, and system stations reject all edits outright, so the "checkpoint flag flips out from under a checked-in order" scenario this used to flag can no longer happen.
- **`assignedStationId` has no role-based gate.** Any user can be assigned to a station regardless of role (§4d) — only frontend UI convention is expected to limit the picker to Station Worker accounts. Worth confirming this is fine, or whether Management/Supervisor should be blocked from ever getting one.
- **No periodic cleanup of expired/revoked refresh tokens (§4e).** The `refresh_tokens` table only grows — fine now, worth a scheduled prune job before heavier production use.
- **No "log out everywhere" endpoint (§4e).** `POST /auth/logout` revokes one device's refresh-token family at a time; revoking every session for a user at once isn't built (deactivating the account achieves the same end result, since deactivated users are rejected on refresh).
- **~~Not yet deployed~~ — deployed 2026-08-19.** §4b–§4e all shipped to production via a full wipe-and-redeploy (see §2). Any *new* local change from this point forward reintroduces drift until it's deployed again.
- **A stale bearer token issued by a previous JWT-payload shape 500s instead of 401ing.** Surfaced right after the 2026-08-19 redeploy: `GET /auth/me` (and anything else reading `request.user.roleId`/`roleName`) assumes the JWT payload always has that shape; a token signed before the roles/permissions refactor (plain `role` enum, no `roleId`/`roleName`) still passes signature verification but fails response schema validation, producing a 500 instead of a clean 401. Self-resolves as old tokens expire or get replaced by fresh logins (now within 15 minutes, per §4e) — not hotfixed, since this is an inherent side effect of ever changing a JWT payload shape, not specific to this deploy. Worth a small defensive fix later (validate the decoded payload shape in `fastify.authenticate` and 401 on mismatch) if it becomes a recurring nuisance after future auth changes.
- **No recovery runbook for a total admin lockout.** §4c's lockout guard prevents the common accidental case, but there's deliberately no superuser bypass — if the guard itself had a bug, or every Management credential were lost some other way, recovery means direct SQL/Prisma Studio against `role_permissions`/`users`. That procedure hasn't actually been written down anywhere yet.
- **No roles/permissions admin UI.** Same pattern as stations/catalog: `/roles` and `/permissions` are ready, but there's no screen yet for Management to build a custom role or reassign users without hand-crafting API calls.
- **Concurrent admin-edit race on the lockout guard is a known, accepted gap, not a fix.** Two simultaneous edits by different Management users could theoretically both pass the "at least one admin remains" check and jointly zero out coverage (Postgres read-committed isolation, not `SERIALIZABLE`). Judged extremely unlikely for this app's actual usage pattern (one small admin team), so left as-is rather than adding row locks.
- **Single Fastify process, no horizontal scaling.** PM2 runs one instance (`fork` mode, not `cluster`). Fine at current expected load; would need revisiting if usage grows.
- **QR scanning UI itself doesn't exist yet.** The API supports it (`/scan/receive`, `/scan/outgoing`, `GET /orders/:id/qr`), but there's no camera-scan web page for station staff to actually use on a phone/tablet — that's frontend work, not yet started.
- **No automated test suite.** Verification so far has been manual smoke-testing (documented happy-path, rework loop, return-to-sender, RBAC, and negative-path runs) — no `npm test` exists.
- **No staging environment.** The product-catalog deploy briefly took production down: the generated Prisma client defaulted to ESM output on the VPS (differently than it had locally) and crash-looped under the CommonJS build. Fixed by pinning `moduleFormat = "cjs"` explicitly in `schema.prisma`, but a staging step would have caught it before it was public.
- **Product images are URLs only, no upload endpoint.** Management has to host an image somewhere else first and paste the URL in — there's no "upload a photo from your phone" flow.
- **No catalog picker UI either** — same situation as the scan UI: the API is ready (`/categories`, `/products`), but there's no frontend screen yet for staff to browse category → product → color lining during intake.
- **No stations admin UI either** — same pattern again: `/stations` is ready for Management to configure the production line, but there's no screen for it yet.
- ~~The published concept guide is now stale~~ — refreshed 2026-08-19 (§5), now matches dynamic stations/roles, refresh tokens, and station-worker locking.
- **Client-facing ordering portal** — fully out of scope, not designed. The new `Customer` model (§4o) is deliberate prep for this — `name`/`phone`/`email` (unique) exist today, but no auth fields (`passwordHash`, `emailVerifiedAt`, etc.) have been added, since Phase 1 doesn't build the portal itself. Adding those later is a safe, additive migration whenever that work actually starts.
